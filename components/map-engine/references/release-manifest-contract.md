# Private draft, current final evidence, and legacy release identity

## New complete maps — v1.4

New production can complete through a concise `release-manifest.json` with `manifest_version: "1.4"`. It requires exact artifact and source identities, one independent actual-artifact final report, and Ben's exact acceptance for accepted status. No socket graph, staged proof reports, or separate file per claim is required. Do not migrate old rejected/accepted records into this format or manufacture new historical evidence.

Use `root: "."`, `status: "candidate"` or `"accepted"`, production `author`, existing `commission`, `provenance_note`, `known_limitations`, `unperformed_checks`, `artifacts`, `lineage_inputs`, and `excluded_identities`. File identities and source/exclusion rules are the same as the draft route below. Complete candidates have no unresolved limitations or unperformed required checks; retain harmless advisories in the review rather than hiding them. Each artifact has `release_artifact: true`, `disposition` matching manifest status, and `release_eligible: false` for candidate or `true` for accepted. Exactly one has role `player_map`; include requested gridded/GM derivatives in the reviewed artifact list.

`independent_review` is a local `{path, sha256}` record for a single final JSON report. The report identifies `reviewer` (different from `author`), `context: "fresh-actual-artifact"` or `"independent-targeted-recheck"`, `status: "pass"`, and `artifacts` as an ordered array of exact `{path, sha256}` identities with uppercase hashes. It repeats the manifest's exact `lineage_inputs` and `excluded_identities`, records `unresolved_material_findings: []`, and supplies `claims` for `tactical`, `lineage`, `native_scale`, `cold_authorship`, and `beauty`. Each claim has `status: "pass"` and concrete `evidence` from the actual map or applicable preserved evidence. These are five distinct claims in one review, not five reviewers or files. The owner must verify actual independence, capability, cold inspection, and evidence quality; strings do not prove a review occurred.

An informed targeted recheck uses `context: "independent-targeted-recheck"` and names the immutable original report in `original_cold_review: {path, sha256}`. That original report preserves its independent `reviewer`, `context: "fresh-actual-artifact"`, original `status` (pass or fail), and exact original `artifacts` identities. Do not alter its findings or pretend the recheck is blind. The final report adds concise `affected_scope` and `recheck_evidence` describing the defect, affected regions/claims actually inspected, the correction observed, and why preserved evidence still supports unchanged claims. The same independent reviewer may perform the recheck; a new blind reviewer is unnecessary. Exact final artifact/source binding and independent reviewer identity remain required. Further targeted corrections may still reference the original cold report while retaining intervening findings in the existing production record; no report chain or extra phase is required.

A candidate has `decision: {"status": "pending"}`. For acceptance, set `decision` to `{status: "accepted", by: "Ben", record: {path, sha256}}`. The hashed JSON decision record contains `status: "accepted"`, `by: "Ben"`, the exact ordered `artifacts` identities, and nonempty `instruction_source` and `instruction_quote` recording his actual instruction. Retrieve that instruction before recording it; agents cannot create consent by writing a decision file. The validator rejects absent evidence, wrong subject/owner, mismatched bytes, missing or self-authored review, unperformed claims, and prohibited declared lineage. It cannot authenticate a fabricated quote or discover omitted history; source inspection and honest provenance remain necessary.

Run `python scripts/validate_release.py path\to\release-manifest.json --require-review-admission` to confirm a complete candidate can enter final private review; run `--require-accepted` for an accepted exact artifact. Acceptance does not authorize publication, deployment, or live VTT. Those actions still require Ben's applicable explicit instruction. A new complete Story reader can use this current evidence route without recreating legacy phase machinery.

## New private work in progress — DRAFT-ONLY

Within an authorized adventure commission, use a separate `draft-manifest.json` for new unfinished art in a private local reader/offline review. This is identity and scope evidence, not a quality verdict. The consumer must visibly label the reader DRAFT-ONLY and show known missing assets/checks outside the adventure prose. Do not rename or overwrite an existing release manifest.

Run `python scripts/validate_release.py path\to\draft-manifest.json --draft-only`. This route never returns `review_ready` or `release_ready`; only `draft_ready` may be true. It cannot be combined with the strict review/accepted flags. A consumer must explicitly choose this private draft mode; no accepted/live consumer may silently fall back to it.

The draft record contains `draft_version: "1.0"`, `status: "draft-only"`, `label: "DRAFT-ONLY"`, `scope: "private-local-review"`, `root: "."`, and `decision: "pending"`. Name the existing authorized `commission` and source history in `provenance_note`; include arrays `known_limitations` and `unperformed_checks` with actual omissions (empty only when none remain). No automatic PASS is inferred from an empty array.

`artifacts` names each local path, SHA-256, and role (including a `player_map`), with `disposition: "draft-only"`, `release_artifact: false`, and `release_eligible: false`. `lineage_inputs` names every imported production source by local path/hash, `classification: "admitted-source"`, and `release_eligible: false`. A fresh source-free drawing may have no lineage inputs; explain that provenance. Copy only clean authorized sources into the bounded package. Excluded history stays outside it.

Carry all relevant rejected, superseded, contaminated, and inspection-only identities from the owning artifact history into `excluded_identities`, each with `sha256` and `reason`. The checker rejects matching artifact/source bytes, corrupt hashes, path escapes, duplicate paths, misleading flags, and excluded source classifications. It cannot discover an omitted historical identity or prove an honest source declaration: the owner must inspect lineage and preserve historical evidence. Do not use this route to relabel rejected art or to claim quality by changing the validator.

One independent report may cover the actual final draft's relevant claims; there is no required graph, pre-finish report, or report-per-claim chain for this private mode. When the new artifact is complete, record its actual final evidence through v1.4 above. Do not turn a draft flag into an accepted decision.

## Existing strict v1.3 release and review records

`release-manifest.json` is the sole eligibility record for one candidate. It is not a directory inventory and it does not grant publication authority. Version 1.3 refuses release validation until its construction graph cites a passing asset-sufficiency audit, immutable passing pre-finish blockout review, complete aesthetic contract, immutable passing pre-finish beauty proof, real admitted asset bytes, and final reports bound to the exact player-map subject. Version 1.2 records remain historical and are never silently rewritten as v1.3.

### Legacy v1.3 required behavior

- Name the brief, frozen v1.3 construction graph, metrics, five final verification records, every candidate/release artifact, important lineage inputs, and rejected predecessors by exact SHA-256. The graph itself shall hash-lock the asset audit, blockout and report, aesthetic contract, and beauty proof and report.
- Keep `release_artifact` separate from `release_eligible`: a player map can be intended for release while still ineligible pending Ben's existing final gate.
- `candidate`, `rejected`, `superseded`, and `benchmark-only` manifests may not mark any artifact eligible.
- Private review admission is distinct from release eligibility. Only an explicitly owner-authorized private local reader or offline preview may use an exact valid v1.3 `candidate` or `accepted` artifact after the review-admission validator passes. It does not alter a candidate's pending decision or any artifact's `release_eligible` field, and it never authorizes publication, deployment, live VTT use, or accepted-only downstream integration.
- `accepted` requires a closed asset-production lane, zero unresolved asset gaps, a passing unprimed blockout review, a passing fresh unprimed beauty proof, all five final verification tracks, a recorded accepted decision, and one accepted primary player map. A construction pass cannot compensate for a beauty failure, and a beauty pass cannot compensate for a construction failure.
- Rejected, superseded, benchmark-only, and v1.2 historical records are not review-product inputs. They remain inspectable evidence only. Downstream readers and VTT tooling must consume only paths selected from a passing accepted manifest.
- A single proof cannot claim cadence maturity. At least two consecutive unrelated timed proofs are the minimum evidence, not an automatic performance claim.
- Every v1.3 graph asset shall exist at its declared path, hash-match, identify one matching `admission: admitted` asset-audit record, and appear as an `admitted-source` lineage input. This verifies source identity and admission rather than trusting an unverified graph label.
- Every v1.3 final verification wrapper shall identify the exact primary player-map path and hash. Its JSON evidence shall repeat the track, outcome, and exact subject; disagreement fails validation.
- An optional Ben owner-quality disposition may preserve an exact later severity judgment only through an exact decision record that binds candidate, original review, claim, severity, and disposition. Its immutable review shall explicitly bind the same finding ID and exact primary player-map path/SHA-256; missing, ambiguous, or different bindings fail. The record name alone is not authorization proof. It cannot soften a `hard_blocker`, change an immutable review, or by itself make a package accepted/release-eligible.
- A v1.2 manifest remains readable historical evidence, but it shall never be release-ready or satisfy the `--require-accepted` integration path.

### Legacy v1.3 validator behavior

Run `python scripts/validate_release.py <manifest>`. The validator checks filename uniqueness, path containment, hashes, Story Engine gate preservation, asset sufficiency, admitted graph source bytes and lineage, closed production-lane status, socket mates, owned joins, standalone-prop exclusion, incompatible bases/shadows, unprimed blockout passage, the complete aesthetic contract, fresh unprimed beauty-proof passage, graph relationships, final-report outcome/subject agreement, five-track independence, eligibility, rejected-candidate quarantine, optional owner-disposition binding, and the cadence-claim floor.

Use `--require-review-admission` only at an explicitly owner-authorized private local reader/offline-preview boundary. It asserts `review_ready: true` only for a valid v1.3 `candidate` or `accepted` manifest; bad hashes, incomplete proofs, excluded statuses, and historical v1.2 evidence fail. The validator cannot create the owner authorization: callers must retain that scope separately. Use `--require-accepted` at downstream integration boundaries. A valid candidate intentionally has `review_ready: true` and `release_ready: false`; that makes exact review possible without making it shippable.
